# LHDC 码率治理的生效条件

治理器的开关表示用户允许使用此功能。Hook 安装成功只表示软件函数表中有模块入口，不能据此认定正在控制当前音频流。

软件治理需要实际的 LHDC 编码回调，才能读取编码器码率并使用队列驱动治理。硬件 A2DP offload 等未经过该回调的路径无法使用这套软件治理；单纯重装软件 Hook 不会接管硬件编码器。

## 平台配置兼容保护（开发中）

治理器开启时增加独立的配置保护后端，适用于当前活动设备的 LHDC V5 固定 1000 配置、系统确认正在播放而软件编码器始终不可观测的情况。治理器关闭时不降码率。

- 连续播放至少 25 秒、软件编码器缺失至少 8 秒，且 30 秒内至少收到两次去重后的可靠耳机卡顿上报，才允许尝试一次 1000 → 900 的系统配置写入。
- 复用系统 `A2dpService.setCodecConfigPreference`，严格保留采样率、位深、声道、codecSpecific2/3/4 及 codecSpecific1 高位。每次写入前重新核对活动设备和完整配置。
- 只有再次读取到匹配的 900 配置才确认保护。写入 API 返回成功只是请求已提交；15 秒没有配置回执时标记超时，不循环重试。
- 一次用户选择最多降档一次，保持 900，避免反复重配置。这个后端暂不提供软件治理器的 500/400 梯度、边界学习或自动回升。
- 关闭治理器或软件编码器重新可控时，仅对模块仍持有的、格式完全匹配的 900 配置恢复原始 1000。手动写入、协议/格式变化和设备切换优先，不覆盖用户新操作。
- bridge 快照分开保留实际传输配置与原始选择；耳机记忆使用原始选择，临时 900 不应被存成用户选择。
- 该后端会重配置音频输入，可能短暂停顿。它不是无缝 DSP 调码率，也没有提供 DSP 实时码率读取。诊断页分别显示待确认、900 配置保护、恢复和失败，实时码率继续显示未知。

本地只读核对已连接 PJZ110 的动态缓冲支持掩码为 31，未覆盖 LHDC V5 的 codec index 19，因此没有通过修改标准 codec 的缓冲参数来声称支持 LHDC。平台配置保护不依赖机型或系统版本硬编码。

## 运行状态

- `encoderState=software`、`encoderControlAvailable=true`：观测到最近的软件编码回调。用户开启治理器且当前为音质优先时，`governorEffective=true`。
- `encoderState=waiting`：尚无可用编码回调。系统播放查询不可用时保持未知；暂停播放也不会被当成硬件 offload。
- 系统连续报告播放、8 秒内始终没有软件编码回调后，进入 `encoderState=monitor_only`。诊断页显示“仅监测”，并提示当前音频路径暂不支持码率治理。该状态不声称已确定硬件会话类型。

模块继续收集 BQR 和耳机卡顿回报，但缺少软件编码回调时不产生新的治理降档目标。确认进入仅监测后，清理该耳机旧的保护上限、恢复试探和待确认事务；保留系统确认的耳机码率能力和其他耳机状态。普通暂停不清除已有保护上限和学习结果。软件编码回调恢复后重新经过起流保护窗口，再恢复正常治理。

## 诊断解释

- `actualBitrateKbps=0` 表示实际码率未知，不表示音频真的以 0 kbps 播放。
- `queue=-1` 或容量未知时显示“—”，不能据此判定队列正常或堵满。
- `ceilingKbps` 是软件治理目标；它与 `actualBitrateKbps` 不同。目标 900 不等于实际已降到 900，目标恢复 1000 也不证明编码器已回到 1000。
- `platformPlayback` 独立记录 `playing` / `idle` / `unknown`，避免把无法观测软件编码器误显示为暂停。

平台配置保护只确认系统配置，不把配置值当作实际编码码率。仍不能承诺固定高码率在拥挤无线环境中不再卡顿；新后端的听感与重配置过程需要设备验收。
